# Entity Relationships: Framework

**Version:** 0.1
**Status:** Discovery / Data Platform Design
**Owner:** Engineering
**Last Updated:** 2026-08-04

## Purpose

Establish the small set of relationship *patterns* used throughout LabPulse's data model, so every relationship in [`relationship-catalog.md`](relationship-catalog.md) is expressed consistently. This document defines the vocabulary; the catalog applies it to every actual entity pair. No SQL or schema is defined here — see [ADR-005](../decisions/ADR-005-canonical-data-model.md) and [ADR-006](../decisions/ADR-006-data-platform-philosophy.md).

## Relationship Patterns

### 1. Ownership hierarchy (scoping)

One entity exists only within, and is scoped by, a parent entity. Deleting or disabling the parent has direct implications for the child. This is the pattern behind tenant isolation.

Example: `Organization -> Office -> Employee`. An Employee cannot exist without an Office; an Office cannot exist without an Organization.

### 2. Produces / derives

One entity is generated by a process acting on another, but does not depend on the source entity's continued existence for its own meaning — it captures a fact "as of" the time it was produced.

Example: `Office -> RevenueSnapshot`. A RevenueSnapshot is produced from an Office's imported revenue data for a period; it remains meaningful (and immutable) even if the Office's other data later changes.

### 3. Evaluates / triggers

One entity is evaluated against another to produce a third. This is the pattern behind business-rule evaluation.

Example: `BusinessRule` evaluates one or more `Snapshot` entities to produce an `Alert`.

### 4. Synthesizes / references as evidence

One entity is produced by combining several others, which it then references as its justification, without owning or duplicating their data.

Example: `Recommendation -> Evidence` (a Recommendation references the Alerts, Metrics, and Snapshot values that justified it, rather than copying their values in).

### 5. Supersession

One entity replaces another of the same type because updated data or rules produced a new conclusion. The old entity is never deleted; the new entity points back to it (and, per [`docs/data-model/03-versioning-strategy.md`](03-versioning-strategy.md), both remain permanently readable).

Example: `Recommendation -> Recommendation` (Superseded By).

### 6. Assignment (many-to-many with scope)

A User is connected to an Office (or Organization) through an explicit assignment record that also carries a SecurityRole and, optionally, an effective date range — never a direct, unscoped link.

Example: `User -> Permission -> Office` (see [`permission-model.md`](permission-model.md)).

## How to Use These Patterns

[`relationship-catalog.md`](relationship-catalog.md) lists every actual relationship in the entity catalog and labels each with one of the six patterns above. When a new entity or relationship is added to the repository, it should be expressed using one of these patterns (or, if none fit, this document should be extended first — patterns should not silently proliferate).

## What This Document Does Not Define

- The literal list of every relationship (see [`relationship-catalog.md`](relationship-catalog.md)).
- Cardinality or foreign-key design (Sprint 3 / database design scope).
- Cascade or referential-integrity behavior (Sprint 3 scope, informed by [`02-data-lifecycle.md`](02-data-lifecycle.md)).
