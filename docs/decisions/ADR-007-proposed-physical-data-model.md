# ADR-007: Proposed Physical Data Model (Sprint 3B, corrected in Sprint 3B.1, Sprint 3B.2, Sprint 3B.3, Sprint 3B.4, and Sprint 3B.4A)

**Status:** Proposed
**Date:** 2026-08-05 (amended 2026-08-06 — see "Amendment: Sprint 3B.1 Corrections," "Amendment: Sprint 3B.2 Corrections," "Amendment: Sprint 3B.3 Corrections," "Amendment: Sprint 3B.4 Corrections," and "Amendment: Sprint 3B.4A Corrections" below)

## Context

Sprint 3A (Decision Reconciliation) resolved the schema-blocking founder/business decisions identified by an independent review pass: SecurityRole MVP scope, the Labor Model/Payroll-Percentage separation, the staffing-unit representation strategy, the backlog production-stage taxonomy strategy, retention/erasure posture, legacy-threshold non-adoption, and franchise-grouping deferral (see [`docs/development/SPRINT_3B_REPORT.md`](../development/SPRINT_3B_REPORT.md) for the full decision list and rationale). With those decisions approved, the conceptual entity catalog ([`docs/entities/`](../entities/)) and logical data platform design ([`docs/data-model/`](../data-model/)) can be mapped to a proposed PostgreSQL/Supabase physical schema — the "Sprint 3 – Database Design" work named in [`docs/development/PROJECT_MEMORY.md`](../development/PROJECT_MEMORY.md) Recommended Next Sprint.

This ADR records that mapping as a **proposal**, not an implementation. No migration, executable SQL, or Supabase project exists as a result of this ADR.

## Options Considered

1. Defer physical schema design further, until every remaining open question (legacy reconciliation, franchise design, exhaustive P&L line items) is resolved.
2. Propose a physical schema now, scoped strictly to what Sprint 3A's decisions and the existing logical design already support, explicitly deferring anything still genuinely unresolved (rejected snapshot types, Notifications, franchise, hard-delete).
3. Propose a physical schema that also guesses at unresolved business meanings (legacy Office attributes, exhaustive account mappings, staffing unit) to move faster.

## Decision

Adopt **Option 2**: propose a physical schema now, scoped to what is actually settled, with every remaining gap named explicitly rather than guessed at (see [`docs/database/09-deferred-entities.md`](../database/09-deferred-entities.md) and the Open Questions sections throughout [`docs/database/`](../database/)).

Key structural choices adopted by this proposal:

- **UUID primary keys**, `TIMESTAMPTZ`/`DATE` per [`docs/database/01-physical-model-principles.md`](../database/01-physical-model-principles.md)'s grain rules, `NUMERIC` (never floating-point) for money and percentages.
- **Lookup tables over native `ENUM`** for any organization-configurable or evolving value set (SecurityRole, JobRole, production stage), preserving "configuration before customization."
- **Header/detail patterns** for PayrollSnapshot, LaborModelSnapshot, and BacklogSnapshot, avoiding fixed-column assumptions about line items, staffing units, and stage taxonomies that are not yet fully confirmed.
- **Normalized join tables, never array columns**, for Permission's office scoping and every Evidence/baseline reference — typed per snapshot type rather than a single polymorphic reference table, to preserve enforced foreign-key integrity.
- **`organization_id` denormalized onto office-scoped tables** to simplify future RLS policy design. **Updated by Sprint 3B.3 (Correction 8):** this sentence originally framed the resulting consistency-enforcement gap as unresolved Sprint 3C work in its entirety; that framing is now stale. Composite foreign keys (Sprint 3B.1 Correction 2, Sprint 3B.2 Correction 2, and Sprint 3B.3 Corrections 1, 3, and 5) now resolve every **unconditional** same-tenant relationship declaratively — this is no longer an open risk. Only two categories remain genuinely open for Sprint 3C: (1) **conditional** global-or-same-organization references, where the target's own `organization_id` is nullable (the eight sites in [`docs/database/01-physical-model-principles.md`](../database/01-physical-model-principles.md) "Global-or-Same-Organization Reference Pattern"), which need a trigger because a plain composite FK cannot express "match, or the target is global"; and (2) `audit_event.entity_type`/`entity_id`, the one deliberate polymorphic reference in this proposal. See [`docs/database/04-keys-relationships-and-constraints.md`](../database/04-keys-relationships-and-constraints.md) "What Remains Genuinely Open for Sprint 3C" for the complete, current residual list.
- **No physical table for ProductionSnapshot, QualitySnapshot, CareerGridSnapshot, RecruitingSnapshot, Notifications, or franchise grouping** — all remain conceptual/deferred.
- **No RLS policy SQL, no migrations, no executable SQL of any kind.**

## Reasons

- Matches [ADR-000](ADR-000-architectural-philosophy.md)'s "configuration before customization," "no hidden business logic," and "traceability" principles more directly than either deferring further (which stalls a milestone the founder has already approved reaching) or guessing (which risks the exact kind of invented business rule [`CLAUDE.md`](../../CLAUDE.md) prohibits).
- The header/detail and lookup-table choices are specifically shaped by named, still-open questions (OQ-011–013, OQ-049, OQ-061, OQ-069) so that resolving those questions later requires new *rows*, not new *columns* or a schema migration — directly reducing rework risk called out as a known project risk in [`docs/development/PROJECT_MEMORY.md`](../development/PROJECT_MEMORY.md).
- Deferring the four incomplete snapshot types, Notifications, and franchise grouping matches the Sprint 3A corrected readiness classification: incomplete product-feature definition is not the same as a schema blocker, and building placeholder tables for undefined concepts is explicitly prohibited by this sprint's authorization.

## Amendment: Sprint 3B.1 Corrections (2026-08-06)

A review pass identified fifteen relational-design issues in the Sprint 3B proposal — none of which reversed a founder-approved business decision, but several of which were genuine engineering errors (an incorrect relational-cardinality claim on Permission Set, a fail-open authorization inference, an immutability model that its own uniqueness constraints made impossible to use). Sprint 3B.1 corrected all fifteen; the full account is in [`docs/development/SPRINT_3B_1_REVIEW_CORRECTIONS.md`](../development/SPRINT_3B_1_REVIEW_CORRECTIONS.md). In summary:

- The `organization_id`/`office_id` consistency gap is now closed **declaratively** via composite foreign keys, for every relationship where a stable composite parent key exists — a materially smaller residual list remains for Sprint 3C than Sprint 3B originally described.
- The `metric_observation` persistence judgment call is now the settled design (durable-evaluation-only persistence, with a component-level replacement for the single numerator/denominator assumption).
- The SecurityRole–Permission-Set relationship direction was corrected (Sprint 3B's claim about dropping a uniqueness constraint was relationally incorrect).
- `employee_office_assignment` is no longer an optional, droppable addition — it is now the sole authoritative source of an Employee's Office, MVP-required.
- `task_status_history` was formally moved to Deferred Entities, resolving that judgment call in the opposite direction (deferred, not included-as-optional).
- The proposal's exact table count changed from 54 (Sprint 3B) to 59 (Sprint 3B.1) — see [`docs/database/02-table-catalog.md`](../database/02-table-catalog.md) for the per-domain breakdown.
- **This ADR's status remains Proposed.** The amendment corrects the proposal's content; it does not change its governance status — Sprint 3D's independent review and founder sign-off are still required before Acceptance.

## Amendment: Sprint 3B.2 Corrections (2026-08-06)

A second, narrower review pass identified ten cross-tenant and revision-integrity issues that Sprint 3B.1 had not caught, plus several further instances of the same failure patterns found during a broader integrity audit. None reversed a founder-approved business decision; all were engineering corrections. The full account is in [`docs/development/SPRINT_3B_2_INTEGRITY_CORRECTIONS.md`](../development/SPRINT_3B_2_INTEGRITY_CORRECTIONS.md). In summary:

- **Metric Observation's uniqueness constraint was wrong** — it blocked a legitimate second observation after a source snapshot was corrected. Corrected with an `evaluation_fingerprint` plus the same revision/supersession pattern already used by the four canonical snapshots.
- **Same-tenant enforcement was extended one level down**, from header tables (covered in 3B.1) to detail and join tables (`payroll_snapshot_line_item`, `labor_model_staffing_measure`, `backlog_stage_count`, the import-lineage detail chain, `metric_observation_component`, the Scenario baseline and Recommendation evidence join tables, and `task`), closing gaps where a plain, unenforced foreign key could in principle connect records from different Organizations or Offices.
- **A new "Global-or-Same-Organization Reference Pattern"** was introduced and documented once, then applied at eight sites where a tenant-owned row references a nullable-organization lookup table (`security_role.permission_set_id`, `permission.security_role_id`, `employee.job_role_id`, and five others) — each requires a Sprint 3C trigger, since a plain composite FK cannot express a conditional "match, or the target is global" rule.
- **`permission_set` gained tenant ownership** (a nullable `organization_id`), closing a gap where one organization could, in principle, have altered another organization's or a global role's capability composition.
- **A real bug in the non-overlap constraints** on `production_stage` and `business_rule_version` was found and fixed: a single `EXCLUDE` constraint including a nullable `organization_id` does not catch two overlapping system-default rows, the opposite of the protection Sprint 3B.1 believed it provided.
- **Snapshot (and now Metric Observation) supersession** must match a row's complete natural key, not merely its organization — closing a real gap where a snapshot could have been recorded as superseding a different Office's row.
- **`alert` can now represent every `business_rule_condition.condition_type`**, not only `numeric`, via two new tables (`condition_evaluation`, `condition_evaluation_evidence`) — the only two new tables this correction pass adds.
- **Recommendation supersession direction was reversed** (`supersedes_recommendation_id` now lives on the newer row), removing a requirement to mutate an already-immutable Recommendation.
- **`employee_office_assignment`'s "append-only" description was corrected** to "effective-dated, historically preserved" — it was self-contradictory as originally stated.
- **The two generic, unenforceable Scenario reference columns were replaced** with two typed, composite-FK-enforced columns (JobRole and Office), the only two target types with any concrete precedent in the repository.
- **The physical ERD's one false relationship line** (`PERMISSION ||--o{ PERMISSION_SET_CAPABILITY`, drawn as if a direct foreign key existed when none does) was removed.
- The proposal's exact table count changed from 59 (Sprint 3B.1) to **61** (Sprint 3B.2) — the two `condition_evaluation`/`condition_evaluation_evidence` tables are the only net addition; every other correction added columns and constraints to existing tables.
- **This ADR's status remains Proposed.** As with the Sprint 3B.1 amendment, this corrects the proposal's content, not its governance status.

## Amendment: Sprint 3B.3 Corrections (2026-08-06)

A third, narrower review pass verified that every composite foreign key introduced by Sprint 3B.1 and Sprint 3B.2 actually had a matching parent-side key declared, and closed several remaining gaps in evidence-table tenant matching, snapshot-to-import integrity, scenario-version binding, validation-result lineage, and same-row check-constraint coverage. None reversed a founder-approved business decision; all were engineering corrections. The full account is in [`docs/development/SPRINT_3B_3_FINAL_CONSTRAINT_COMPLETION.md`](../development/SPRINT_3B_3_FINAL_CONSTRAINT_COMPLETION.md). In summary:

- **Two composite-FK parent keys were missing entirely.** `metric_observation` and `condition_evaluation` each already had composite foreign keys pointing *at* them (from `metric_observation_component`, `condition_evaluation_evidence`, `alert`, and others) with no corresponding parent-side `UNIQUE` constraint ever declared — meaning those composite FKs could not actually have been created. Both now carry the required keys; a full verification matrix confirms every other composite FK in the proposal already had a valid matching parent key.
- **`condition_evaluation_evidence` was missing `office_id` entirely**, which meant its "organization-and-office-matched" snapshot references (claimed since Sprint 3B.2) could not actually be expressed as composite FKs — there was no `office_id` on the row to compose them from. Corrected, along with a new evidence-shape `CHECK` tying `evidence_role` to which reference columns must be populated, ruling out both a mismatched role/reference combination and a fully empty evidence row.
- **The four canonical snapshot headers' `import_job_id` was still a plain, unenforced FK** — the one remaining place in the header-level import-lineage chain where a snapshot could, in principle, be recorded against a different organization's Import Job. Corrected to a composite FK, alongside removing a genuinely duplicated `import_profile_version_id` fact that existed independently on both `import_job` and three snapshot headers with nothing preventing disagreement.
- **Scenario values could reference a Parameter or Output Definition from the wrong Scenario Definition Version** — neither the existing Run-level nor Definition-level foreign keys, individually or together, prevented this. Corrected declaratively via a shared `scenario_definition_version_id` column enforced against both the parent Run and the cited definition.
- **Sprint 3B.2's "considered and declined" decision not to enforce organization-matching on `import_validation_result`/`import_validation_issue` is withdrawn** — it relied on a plausible-write-path argument ("the import pipeline would never do that"), which the founder's instruction explicitly rejects as an integrity mechanism. Both tables are now organization-enforced like every other table in the lineage chain, with `import_validation_issue` additionally constrained to reference a normalized value from the *same source row*, not merely the same organization.
- **Several same-row invariants were previously undocumented as `CHECK` constraints**, including Permission's effective-date ordering, `import_normalized_value`'s exactly-one-of-two-columns rule, `business_rule_condition`'s numeric-fields-only-for-numeric-conditions rule, lifecycle/version/display-order numeric floors, and a new `UNIQUE (condition_evaluation_id)` on `alert` preventing more than one Alert per immutable Condition Evaluation.
- **The stale "deferred to Sprint 3C in its entirety" framing of the `organization_id`/`office_id` consistency gap, in this ADR's own Decision section, is corrected** — see the updated bullet above. The composite-FK pattern is now the resolution for every unconditional case; only the conditional global-or-same-organization references and `audit_event`'s polymorphic reference remain genuinely open.
- The proposal's exact table count is **unchanged at 61** — every Sprint 3B.3 correction added columns, constraints, and keys to existing tables; none added or removed a table.
- **This ADR's status remains Proposed.** As with the Sprint 3B.1 and Sprint 3B.2 amendments, this corrects the proposal's content, not its governance status — Sprint 3D's independent review and founder sign-off are still required before Acceptance.

## Amendment: Sprint 3B.4 Corrections (2026-08-06)

A fourth, narrowly-scoped review pass examined only the import-provenance/lineage subsystem — the Organization, authorization, snapshot, metrics, scenario, Alert, Recommendation, retention, and RLS-preparation designs were explicitly out of scope, having already been treated as settled by the three prior passes. It found that Sprint 3B.1–3B.3's lineage corrections closed every gap at the **Organization** level, but left a more specific gap open: two rows could share an Organization while still having been produced by two different Import Jobs, and nothing before this pass caught that. None of the six corrections below reversed a founder-approved business decision; all were engineering corrections. The full account is in [`docs/development/SPRINT_3B_4_IMPORT_PROVENANCE_CLOSURE.md`](../development/SPRINT_3B_4_IMPORT_PROVENANCE_CLOSURE.md). In summary:

- **A false "enforced transitively" claim in Sprint 3B.3 is withdrawn.** `import_validation_issue`'s relationship to its parent `import_validation_result` was, until this correction, only organization-matched — nothing actually compared the two rows' `import_source_row_id` values, despite Sprint 3B.3 asserting that equality was "enforced transitively." An Issue could in principle cite a Validation Result for one source row while itself declaring a different one. Corrected with a genuine three-column composite FK, made possible by adding `UNIQUE (organization_id, import_source_row_id, id)` (and a new `UNIQUE (import_source_row_id)`, stating the MVP's one-Validation-Result-per-row grain as a real constraint) to `import_validation_result`.
- **Import Job identity is now propagated as a denormalized column**, not left to a multi-hop join, through `import_source_row`, `import_normalized_value`, and the four typed link tables connecting `import_normalized_value` to the canonical snapshot headers — closing the founder's explicit example: "a canonical snapshot that declares one producing Import Job must not cite source rows or normalized values from another Import Job, even within the same Organization." The same rule is extended to the detail-table path (`payroll_snapshot_line_item`, `labor_model_staffing_measure`, imported-path `backlog_stage_count`), using the same "two composite FKs sharing one column value" technique already established for Scenario-version binding in Sprint 3B.3.
- **A second duplicated Import Profile Version fact is removed.** `import_normalized_value.import_profile_version_id` duplicated a fact already fully determined by `import_job_id → import_job.import_profile_version_id`; removed, following the identical principle Sprint 3B.3 already applied to the four snapshot headers.
- **An Import Job's Organization-specific override can no longer target the wrong Profile Version.** The Sprint 3B.2 composite FK on `import_job.organization_import_profile_override_id` verified only that the override belonged to the right Organization, not that it had been defined for the same Profile Version the Import Job itself declares. Corrected to a three-column composite FK requiring both to agree — a distinct, internal-consistency rule that does not conflict with the separate, deliberate decision that two *different* Import Jobs in a supersession chain may use two different Profile Versions.
- **The Payroll account-mapping duplication is resolved by removing the duplicate column.** `payroll_snapshot.account_mapping_version_id` and `import_job.organization_import_profile_override_id` were found to represent the same fact, recorded independently in two places with nothing preventing disagreement — no repository document describes a distinct "account mapping" concept separate from the Import Job's own override. `payroll_snapshot.account_mapping_version_id` is removed; the fact is now derived exclusively through `payroll_snapshot.import_job_id → import_job.organization_import_profile_override_id`.
- **Every "every lineage arrow is an enforced foreign key" claim in this proposal is corrected to state precisely what is enforced**, replacing an imprecise blanket statement with a per-relationship Import-Provenance Integrity Matrix (Organization / Import Job / source row / Profile Version / manual-entry exception, per relationship) in [`docs/database/06-import-lineage-model.md`](../database/06-import-lineage-model.md) — the honest, complete successor to the Sprint 3B.1 statement, which was true only along the Organization dimension.
- **One new, narrow Sprint 3C trigger requirement is named, not silently left undocumented:** a manually-entered `backlog_stage_count` (no Import Job) must belong to a manually-entered `backlog_snapshot` header, never an imported one — this specific cross-row consistency cannot be expressed as a `CHECK` or a plain composite FK (PostgreSQL's `MATCH SIMPLE` foreign-key semantics skip enforcement entirely when the child's `import_job_id` is `NULL`), so it joins the existing residual list in [`docs/database/04-keys-relationships-and-constraints.md`](../database/04-keys-relationships-and-constraints.md) "What Remains Genuinely Open for Sprint 3C" as a seventh item.
- The proposal's exact table count is **unchanged at 61** — every Sprint 3B.4 correction added columns, constraints, and keys to existing tables, or removed a duplicated column; none added or removed a table.
- **This ADR's status remains Proposed.** As with the three prior amendments, this corrects the proposal's content, not its governance status — Sprint 3D's independent review and founder sign-off are still required before Acceptance.

## Amendment: Sprint 3B.4A Corrections (2026-08-06)

A fifth, narrow review pass reconciled two specific gaps Sprint 3B.4 itself left open, and corrected several documentation contradictions Sprint 3B.4 introduced or left un-annotated elsewhere in the proposal. Scope remained the import-provenance/lineage subsystem only; the Organization, authorization, snapshot, metrics, scenario, Alert, Recommendation, retention, and RLS-preparation designs remained out of scope, as settled by the four prior passes. None of the corrections below reversed a founder-approved business decision; all were engineering corrections. The full account is in [`docs/development/SPRINT_3B_4A_FINAL_RECONCILIATION.md`](../development/SPRINT_3B_4A_FINAL_RECONCILIATION.md). In summary:

- **An Import Job's supersession chain enforced only same-Organization, permitting an unrelated base Import Profile into the same chain** — nothing before this pass stopped a Payroll Import Job from being recorded as superseding an unrelated Labor Model, Backlog, or Power BI Import Job, provided both belonged to the same organization. Corrected: `import_job` gains a direct `import_profile_id` (independent of which version), and `supersedes_import_job_id`'s composite FK is strengthened to require the same base Import Profile, not merely the same Organization. Profile-*version* equality across a supersession remains deliberately not required, per the existing Sprint 3B.3 judgment call — this correction operates on a coarser, mandatory identity (the base profile) and does not conflict with that permissiveness.
- **Nothing verified that an Import Job's Profile Version was actually permitted to produce the canonical target its output snapshot claims to be** — a Labor Model profile could, in principle, have produced a `payroll_snapshot` row, with every Organization and Import Job foreign key still perfectly valid. Corrected: `import_profile_version.schema_definition` (already a justified, versioned `JSONB` document) is now required to declare which of the four MVP canonical target codes (`revenue_snapshot`, `payroll_snapshot`, `labor_model_snapshot`, `backlog_snapshot`) that specific version is permitted to produce — a profile version may legitimately permit more than one. A named Sprint 3C trigger requirement verifies each canonical header's producing Import Job used a compatible Profile Version; the four typed link tables and imported-path detail rows inherit this compatibility transitively through their existing same-Import-Job composite FK to their header, needing no separate check of their own. A manually-entered Backlog Snapshot is exempt, having no Import Job to validate.
- **Several documentation contradictions left by Sprint 3B.4 are corrected**, so a reader cannot mistake superseded text for the current controlling design: the Sprint 3B.2 historical composite-FK table in [`docs/database/04-keys-relationships-and-constraints.md`](../database/04-keys-relationships-and-constraints.md) is annotated to mark the six rows Sprint 3B.4 later strengthened; the Sprint 3B.3 "Validation-Result Lineage Integrity" section's now-false "enforced transitively" claim is explicitly withdrawn in place, rather than left standing beside its actual correction elsewhere in the same document; a stale reference to the removed `payroll_snapshot.account_mapping_version_id` column in the Uniqueness Constraints table is corrected; and the "Complete List of Sprint 3C Triggers" — which had omitted the manually-entered-Backlog-header-must-be-manual trigger Sprint 3B.4 itself introduced — now includes it, alongside the two new triggers this pass adds.
- **The physical ERD's cardinalities are corrected in four places**, all understating or overstating what the physical design actually enforces: `IMPORT_SOURCE_ROW → IMPORT_VALIDATION_RESULT` (zero-or-many corrected to zero-or-one, matching the actual `UNIQUE (import_source_row_id)` constraint from Sprint 3B.4); `PAYROLL_SNAPSHOT_LINE_ITEM`'s "1 row : 1 detail row" label (removed — no such `UNIQUE` constraint exists); `IMPORT_JOB ↔ BACKLOG_SNAPSHOT` (corrected from zero-or-one to zero-or-many on the Backlog Snapshot side, since one imported file may cover multiple Offices); and `ORGANIZATION_IMPORT_PROFILE_OVERRIDE ↔ IMPORT_JOB` (direction and cardinality both corrected — each Import Job uses zero-or-one override; each override may be reused by zero-or-many Import Jobs, not the reverse the diagram previously implied).
- The proposal's exact table count is **unchanged at 61** — both Sprint 3B.4A corrections added only columns and constraints to existing tables (`import_job`, `import_profile_version`); no table was added or removed.
- **This ADR's status remains Proposed.** As with the four prior amendments, this corrects the proposal's content, not its governance status — Sprint 3D's independent review and founder sign-off are still required before Acceptance.

## Conditions for Revisiting

Revisit if:

- Sprint 3D's independent review identifies a structural flaw not already caught by the Sprint 3B.1, Sprint 3B.2, Sprint 3B.3, Sprint 3B.4, or Sprint 3B.4A correction passes.
- A founder decision on a currently-deferred item (Notifications, franchise, hard-delete/erasure) requires a new table or a materially different shape than what this proposal's deferred-entity placeholders anticipate.
- Sprint 3C's RLS policy design finds that the composite-FK tenant-consistency pattern, or any of the eight Global-or-Same-Organization Reference Pattern trigger sites, does not hold up under real policy-writing, requiring a schema change before RLS can be implemented safely.
- A real Scenario requirement emerges needing a reference target type beyond JobRole or Office, requiring a new typed column (additive, not a redesign).
- A future Import Profile type is confirmed that legitimately needs to supersede a job from a *different* base Import Profile (for example, a platform-initiated migration from one profile type to a successor profile type) — this proposal's same-base-Profile supersession requirement (Sprint 3B.4A Correction 1) would need to be revisited as a distinct, explicitly-approved exception, not silently loosened.
